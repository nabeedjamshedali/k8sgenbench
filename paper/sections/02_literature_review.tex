\section{Literature Review}\label{sec:literature}

We first review misconfigurations in human-written Kubernetes manifests and the tools that assess them. We then review the security of LLM-generated code and LLM-based generation of infrastructure configurations. Next come studies of LLM-generated Kubernetes manifests and of LLM-based repair and hardening. Finally, we state the gap (Section~\ref{sec:lit-gap}).

\subsection{Misconfigurations in human-written Kubernetes configurations}\label{sec:lit-human}

Rahman et al.\ first studied security problems in infrastructure as code (IaC) systematically. They identified seven security smells in Puppet scripts, such as hard-coded secrets, admin-by-default settings and the use of HTTP without TLS. They detected more than 21,000 smell occurrences in over 15,000 scripts \citep{rahman2019sevensins}. For Kubernetes, Shamim et al.\ collected practitioner knowledge from 104 Internet artefacts. They organised it into eleven recommended security practices \citep{shamim2020xicommandments}. Examples are role-based access control for least privilege, pod- and network-specific security policies, and separate namespaces for workloads.

The most complete empirical study of Kubernetes security misconfigurations analysed 2,039 manifests from 92 open-source repositories \citep{rahman2023k8smisconfig}. It identified 11 misconfiguration categories: absent resource limits, absent security context, activation of hostIPC, hostNetwork and hostPID, capability misuse, Docker-socket mounting, privilege escalation, hard-coded secrets, insecure HTTP and privileged security contexts. In total, 1,051 misconfigurations affected 13.9\% of the analysed Kubernetes objects. Larger manifests were more likely to be misconfigured. Beyond security, \citet{zhang2026k8sconfigdefects} studied 719 configuration defects in 2,260 Kubernetes configuration scripts from 185 repositories. They derived 15 defect categories, and six of them are unique to Kubernetes (e.g., pod scheduling, volume mounting and orphaned resources). They also showed that eight static analysis tools could detect only 8 of the 15 categories. Studies of Helm charts point the same way. \citet{minna2025helm} analysed over 5,000 rendered Helm charts from Artifact Hub. The most frequent misconfigurations concerned resource quotas, network policies and security profiles that are hard to configure. Ghorab et al.\ found that only 21.43\% of the misconfigurations in incubator Helm charts were fixed by the time the charts reached the stable stage \citep{ghorab2026inthewild}.

We use the taxonomies from these studies. However, they observe only human-written configurations, and nearly all analyse the manifests statically without deploying them.

\subsection{Standards and tools for assessing Kubernetes configurations}\label{sec:lit-tools}

Several authoritative guidelines define what a secure Kubernetes configuration should look like. They include the NSA/CISA Kubernetes Hardening Guide \citep{nsacisa2022k8shardening}, the CIS Kubernetes Benchmark \citep{cis_k8s_benchmark} and the OWASP Kubernetes Top Ten \citep{owasp_k8s_top10}. They also include the Kubernetes Pod Security Standards, which define \emph{privileged}, \emph{baseline} and \emph{restricted} profiles for pods \citep{k8s_pod_security_standards}. Open-source static scanners put these guidelines into practice. Kubescape \citep{tool_kubescape}, Trivy \citep{tool_trivy} and Checkov \citep{tool_checkov} focus mainly on security. kube-score \citep{tool_kubescore}, Polaris \citep{tool_polaris} and KubeLinter \citep{tool_kubelinter} also cover reliability best practices, such as probes, resource requests and replica counts. Schema validators such as kubeconform check manifests against the official Kubernetes API schemas \citep{tool_kubeconform}.

However, the evidence on whether these tools agree is mixed. \citet{krieger2026k8sscanners} compared eight compliance standards and ten configuration scanners on a benchmark of 79 recommendations. Only two scanners reached an F1-score of at least 0.69 and also covered at least half of the recommendations. Severity ratings were also inconsistent across tools. \citet{kapetanidou2025k8sscanning} likewise recommended combining static analysers with in-cluster workload scanning. \citet{lanciano2023declarative} used Polaris findings as quality labels for manifests. This has two implications for empirical studies. First, relying on a single scanner risks tool-specific bias. Second, static verdicts need to be complemented by observations of runtime behaviour.

\subsection{Security of LLM-generated code}\label{sec:lit-llmcode}

Pearce et al.\ prompted GitHub Copilot with 89 scenarios based on the MITRE CWE Top-25. They found that about 40\% of the 1,689 generated programs were vulnerable \citep{pearce2022asleep}. \citet{khoury2023chatgptsecure} reported that only 5 of 21 programs written by ChatGPT were initially secure. Yet the model could explain the relevant vulnerabilities when asked. So it had security knowledge but did not apply it unprompted. In real projects, Fu et al.\ found security weaknesses in 29.5\% of Python and 24.2\% of JavaScript snippets generated by AI assistants and committed to GitHub. These weaknesses spanned 43 CWE categories \citep{fu2025copilotweaknesses}. At scale, the CyberSecEval benchmark showed that LLMs suggested insecure code in about 30\% of test cases. More capable models tended to produce insecure code more often \citep{bhatt2023cyberseceval}. BaxBench combined functional tests with executed security exploits. Even the best model generated correct backends in only 62\% of cases, and about half of the correct programs were exploitable \citep{vero2025baxbench}.

These studies consistently show that functional correctness does not imply security. They also show that LLMs tend to omit security measures unless explicitly asked. However, they focus on imperative application code. In declarative configurations, security and reliability depend largely on \emph{what is omitted}. Examples are a missing security context, probe or resource limit. This kind of failure has received far less attention.

\subsection{LLM-based generation of infrastructure and cloud configurations}\label{sec:lit-iac}

Ansible Wisdom is an early example of LLM generation of declarative IT configurations. It fine-tuned a code model on Ansible YAML and evaluated it with text-similarity and schema-correctness metrics \citep{pujar2023ansiblewisdom}. CloudEval-YAML introduced 1,011 hand-written cloud-native configuration problems for Kubernetes, Envoy and Istio. Each problem comes with a unit test that runs on a real cluster \citep{xu2024cloudevalyaml}. Across 12 models, the best model (GPT-4) achieved a unit-test score of only 0.515. Open models of that time performed much worse. For Terraform, IaC-Eval provided 458 AWS scenarios with intent specifications. On these, the best model achieved a pass@1 of only 19.36\% \citep{kon2024iaceval}. TerraFormer improved generation through fine-tuning with feedback from formal verifiers and policy checks \citep{jana2026terraformer}.

More recent studies focus on deployability and security. Zhang et al.\ evaluated LLM-generated AWS CloudFormation templates by actually deploying them. First-attempt deployment success was only 20.8--30.2\% across six LLMs. Even after iterative refinement, requirement coverage (25.2\%) and security compliance (8.4\%) remained low \citep{zhang2026iacgen}. Santos Vargas et al.\ benchmarked seven proprietary and open-weight models on Terraform generation with Checkov and Trivy. They concluded that syntactic validity and security compliance are ``largely orthogonal''. The best configuration reached only 23.1\% Checkov compliance \citep{santosvargas2026secureterraform}. For Ansible, the execution-based ITAB benchmark showed that no open-source model exceeded 12\% pass@10 on real user tasks \citep{hassan2026itab}. For Kubernetes, \citet{kozachok2026k8sdistillation} used staged validators, including kubeconform, to adapt small language models to manifest generation. FDE-Bench evaluated LLM agents on 136 deployment-configuration tasks, including Kubernetes, with gated checks for build, readiness, behaviour and conformance. Resolution rates were 52.9--75.0\%, and readiness was the main failure stage \citep{ding2026fdebench}.

These works show that validity, deployability and security diverge, so each one has to be measured. However, their evaluations use curated or synthetic tasks with reference solutions. None of them compares LLM outputs with the configurations that developers actually maintain for real applications. Also, none examines how the generated configurations behave under failures.

\subsection{Studies of LLM-generated Kubernetes manifests}\label{sec:lit-llmk8s}

Two studies directly examine the quality of LLM-generated Kubernetes manifests. \citet{zhang2024genaismells} mined 98 ChatGPT-generated manifests from developer conversations in the DevGPT dataset (collected in July and August 2023) and analysed them with KubeLinter. Unset CPU and memory requirements were the most frequent smells, and each affected 35.8\% of the manifests. Next came missing read-only root file systems and containers not required to run as non-root. The authors explicitly called for ``a comparative evaluation of generative AI techniques''. They noted that their findings were limited to one model, one tool and manifests of unknown origin. Tabibpour and Dakhilalian then compared 1,985 human-written manifests from the corpus of Rahman et al.\ with the published measurements of those 98 ChatGPT manifests \citep{jcomsec2026aivshumank8s}. They used six KubeLinter smells and a size-balanced resampling analysis. Missing CPU and memory specifications were the most robust weakness of the AI-generated manifests. In contrast, missing \texttt{runAsNonRoot} and \texttt{readOnlyRootFilesystem} settings were common in both corpora.

These studies give the first evidence that LLM-generated manifests inherit known weaknesses and sometimes amplify them. The authors themselves acknowledge several limitations. The human and AI corpora are unmatched and differ greatly in size. The AI corpus reflects a single 2023 model rather than current LLMs. The analysis relies on a single tool, and no manifest is run in a cluster \citep{jcomsec2026aivshumank8s}.

\subsection{LLMs for detecting, repairing and hardening Kubernetes configurations}\label{sec:lit-llmsec}

A separate line of research uses LLMs to analyse or improve existing Kubernetes configurations. GenKubeSec fine-tuned models to detect, localise, explain and fix misconfigurations across 276,520 configuration files. It matched rule-based tools in precision and exceeded them in recall. In contrast, off-the-shelf models, including ChatGPT, Gemini and Claude, detected misconfigurations poorly (best F1 $\approx$ 0.51) \citep{malul2024genkubesec}. Ghorab and Saied showed that a fine-tuned Llama-3 model detected more issues than rule-based tools, especially for probes and resources \citep{ghorab2025k8sllm}. For repair, LLMSecConfig combined Checkov findings with retrieval-augmented generation. It reported large differences between models. Mistral Large 2 had a 94.3\% repair success rate, while GPT-4o-mini had 40.2\% \citep{ye2025llmsecconfig}. \citet{minna2025helm} found that LLM-produced fixes for Helm chart misconfigurations can satisfy scanners but still delete unrelated configuration and break the application. Ghorab et al.\ showed that schema-guided correction raises LLM repair accuracy to 98.5\% \citep{ghorab2026inthewild}. Other work uses runtime context. KubeGuard derived least-privilege roles, network policies and deployments from runtime logs \citep{sgancohen2025kubeguard}. KuTIE showed that LLM security patches that ignore the live service topology are correct in only 11.1\% of topology-dependent cases \citep{shaikh2026kutie}.

These works also show that models disagree and that a scanner-compliant configuration can still break a running service. However, all of them start from an existing manifest. None asks how good an LLM is when it must write the complete configuration of an application from a requirements description. Developers already use LLMs in this way \citep{zhang2024genaismells}.

\subsection{Research gap}\label{sec:lit-gap}

Table~\ref{tab:related} compares the most closely related studies with the present work. The review shows five gaps.
\begin{enumerate}
    \item \textbf{Real-project comparison.} Existing generation benchmarks evaluate curated tasks. The only human-versus-AI Kubernetes comparison uses unmatched corpora. No study compares LLM-generated configurations with the human-written configurations of the \emph{same} applications, generated from the same requirements.
    \item \textbf{Current LLMs.} Evidence on LLM-generated Kubernetes manifests relies on a single 2023 ChatGPT corpus. Current proprietary and open-weight models have not been systematically compared, and neither has their consistency across repeated generations.
    \item \textbf{Reliability.} Research on LLM-generated configurations focuses on security. Reliability controls, such as probes, resource requests, replicas, disruption budgets and anti-affinity, have been studied only for human-written configurations.
    \item \textbf{Runtime resilience.} Prior work stops at static analysis or, at most, checks whether a configuration reaches a ready state. No study injects failures to measure whether generated configurations recover and keep the service available.
    \item \textbf{Linking static and runtime evidence.} Scanners disagree with each other, and scanner-compliant configurations can still fail at runtime. Yet no study evaluates the same configurations across static correctness, security, reliability, deployment and recovery to test whether static findings predict runtime behaviour.
\end{enumerate}
This study addresses these gaps. It compares human-written configurations with those of five current LLMs for the same projects. It uses a six-dimension benchmark that covers static analysis, requirement satisfaction, real deployment and fault injection.
